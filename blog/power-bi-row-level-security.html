Power BI Row-Level Security Explained With Simple Examples

Learn Power BI row-level security with static and dynamic RLS examples. Create security roles, test report access, and share reports securely.

NK
Nathalie
Consultant, Tycoon Clap
4 min read
Quick answer

Power BI row-level security (RLS) filters the records a report viewer can see. Define the rules on the semantic model, assign people to security roles, and test with real viewer accounts. Use a static rule for a fixed group or a dynamic access table for users who cover different territories.

Last updated November 2026

What row-level security does in Power BI

Imagine a U.S. distributor with Southeast and Pacific Northwest sales teams. The Southeast manager should see Atlanta and Charlotte orders. The Pacific Northwest manager should see Seattle and Portland orders. Both open the same dashboard, but totals and detail rows reflect their authorized territories.

RLS enforces rules in the semantic model. It is useful when users share a report and its structure, but access different rows. Hiding a page, removing a visual, or setting a slicer only changes the report presentation. Workspace Admins, Members, and Contributors have editing privileges and are outside the service’s normal RLS enforcement. Give report consumers only the access they need.

Power BI RLS tutorial: Create a static territory role

  1. In Power BI Desktop, model a Territory dimension with one row per territory key. Relate it one-to-many to the Sales fact table and verify that a territory filter reaches sales rows.
  2. Open Modeling → Manage roles, create a role named Southeast Sales, select the Territory table, and use the rule below.
  3. Open View as, choose the role, and compare the sales total and order count with a trusted Southeast-only extract.
  4. Publish the semantic model. In the Power BI service, open the model’s Security settings and add the appropriate users or supported groups to the role. Grant access to the report or app separately.
'Territory'[TerritoryName] = "Southeast"

This approach is easy to review when each group has a fixed filter. If managers often move between territories or oversee multiple territories, use a mapping table and one dynamic rule.

Power BI dynamic row-level security with a user access table

Build a UserAccess table with one row per authorized identity and territory pair. Use real Microsoft Entra user principal names in production. The identities below are fictional.

UserUPNTerritoryKey
casey@example.comSE
morgan@example.comPNW
jordan@example.comSE
jordan@example.comPNW

For a simple Import model, keep the mapping disconnected from the fact table. In one role, set this DAX filter on Territory. The active Territory-to-Sales relationship carries the restriction to orders:

VAR ViewerUPN = USERPRINCIPALNAME()
VAR CurrentTerritory = 'Territory'[TerritoryKey]
RETURN
    COUNTROWS(
        FILTER(
            'UserAccess',
            'UserAccess'[UserUPN] = ViewerUPN
                && 'UserAccess'[TerritoryKey] = CurrentTerritory
        )
    ) > 0

Also filter UserAccess in the same role with 'UserAccess'[UserUPN] = USERPRINCIPALNAME() so viewers cannot query other users’ mapping rows. Give eligible consumers membership in this dynamic role. Casey should see SE, Jordan should see both keys, and a role member with no mapping should see no sales. Model refresh controls how quickly mappings stored in an Import model take effect. For a DirectQuery model, validate supported DAX and source-security options before adapting this example.

Test Power BI security roles before sharing

  • Test a single-territory viewer, a multi-territory viewer, and a viewer whose UPN is missing from the access table.
  • Check totals, detail tables, drill-through, and any sanctioned exports. Confirm that separate facts like budgets or shipments have their own valid security path.
  • Use an actual unprivileged account before launch. Viewer, app, and model permissions should match the production path. DirectQuery with SSO requires a real viewer for testing.
  • Audit overlapping roles. Power BI combines allowed rows from multiple RLS roles, so a broad role can expand a viewer’s effective access.
  • Assign an owner for mapping updates, review access after staff changes, and confirm exports are appropriate for the audience.

See Microsoft’s Power BI RLS documentation for identity and testing details.

RLS vs. object-level security and Report Server

Use RLS to filter which records a viewer sees. Consider Power BI object-level security (OLS) for restricted tables or columns, such as cost rates. A visual that depends on a restricted object can fail for those viewers, so test the consumer experience. For legacy Reporting Services and Power BI Report Server deployments, validate on-premises identity behavior and data-source limitations in the target environment.

See Microsoft’s OLS guide, the Report Server RLS guide, and our SSRS to Power BI migration walkthrough.

Frequently asked questions

Why can a workspace Contributor see all rows?

Contributors have editing rights. For a realistic RLS check, use a viewer who has the intended report and semantic model permissions.

Can one user see multiple territories?

Yes. Create one authorized mapping row per viewer and territory, then test both permitted and excluded territories.

Can RLS hide a salary column?

RLS filters records. Consider object-level security or a separate model when viewers should have no access to a sensitive column.
